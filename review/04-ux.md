# User experience

Judged by reading. Nothing here was observed on screen — there is no toolchain on this machine,
so no build was run. `ROADMAP.md` is emphatic that this is the weakest evidence for this codebase
in particular; treat everything below as worth checking in a GUI pass rather than as settled.

The custom window frame (`ui/window.rs`) is new, untracked, and has no invariants recorded in
`CLAUDE.md` yet. Three of the four findings are there, which is what you would expect of the
newest surface.

---

### [Medium] The close button kills every shell in every tab with no confirmation

**Where:** `src/ui/window.rs:45`, `src/app.rs:1330` (`on_exit`).

**Trigger:** Click `×` with four tabs open, one of them running a long build.

**Detail:** `on_exit` flushes the settings save and then:

```rust
for state in self.panes.values() { state.pane.shutdown(); }
```

There is no count of live panes, no prompt, and no distinction between a shell sitting at a
prompt and one with a child running — which Nyx *knows*, because `handshake::State::child_running`
is already tracked per pane and is already read by `sigil.rs:49` and `copy_blocks.rs:26`.

Every mainstream terminal guards this: Windows Terminal confirms on closing multiple tabs,
iTerm2 and Konsole confirm when a process is running. Nyx is more exposed than any of them,
because it draws its own `×` — there is no OS-level window-close mediation to fall back on, and
`ViewportCommand::Close` goes straight through.

Nyx also has every component needed to do better: a toast system, a palette, a modal settings
window, and per-pane `child_running`.

**Impact:** One misplaced click loses every shell's state. Unrecoverable, and the most likely
click to misplace is the one nearest the corner of the screen.

**Fix:** When `panes.len() > 1` or any pane reports `child_running`, make the first `×` click a
confirmation rather than a close. A config key (`window.confirm_close = "multiple" | "running" |
"never"`) fits the existing schema shape.

**Confidence:** Verified in code; unobserved.

### [Medium] The custom title bar drops snap layouts and the system menu

**Where:** `src/ui/window.rs:32-66`, `src/main.rs:176` (`.with_decorations(false)`).

**Detail:** Replacing the native frame costs three Windows behaviours that the current code does
not reimplement:

1. **Snap Layouts.** On Windows 11, hovering the *native* maximize button pops the snap-layout
   flyout. It is triggered by the window returning `HTMAXBUTTON` from `WM_NCHITTEST`, not by
   anything egui can express. A plain `ui.interact` rect gets nothing. On a tiling-heavy Windows
   11 desktop this is a daily-use feature, and it is the single most-noticed loss from a custom
   frame.
2. **Alt+Space.** The system menu (Move / Size / Minimize / Maximize / Close) is gone. That is
   also the keyboard-only path to move a window, and there is no Nyx equivalent — the title bar
   drag is pointer-only.
3. **Double-click-to-maximize on the *tab strip* region.** `drag_action` correctly suppresses
   dragging over tab buttons, but the gap between the last tab and the window controls is only
   80 px wide (`window.rs:27`), so with several tabs open there is very little bar left to
   double-click or drag.

Nyx already owns a window subclass (`win/cursor.rs` installs one with `SetWindowSubclass`), so
the `WM_NCHITTEST` → `HTMAXBUTTON` handling for snap layouts has a natural home and would not
need new infrastructure.

**Impact:** A Windows 11 user loses a window-management feature they use constantly, with no
setting to get the native frame back.

**Fix:** Handle `WM_NCHITTEST` in the existing subclass, returning `HTMAXBUTTON` when the point
is inside the maximize button's rect (and `HTCAPTION` / `HTLEFT` / … for the drag and resize
regions, which would also let Windows do the resize edges natively instead of
`BeginResize`). Alternatively expose `window.decorations = true` as an escape hatch.

**Confidence:** Verified for what the code does; the snap-layout mechanism is documented Windows
behaviour, not something I could test here.

### [Low] The window controls are invisible until the title bar is hovered, but always clickable

**Where:** `src/ui/window.rs:41,51,55-57`.

**Detail:** `controls_visible` gates only the `painter().text(...)` call; the
`ui.interact(button, …, Sense::click())` above it is unconditional:

```rust
let response = ui.interact(button, …, Sense::click()).on_hover_text(hint);
if response.hovered() { /* paint the hover fill */ }
if controls_visible { /* paint the glyph */ }
if response.clicked() { ctx.send_viewport_cmd(command); }
```

So the top-right 132 px of the title bar closes, maximizes and minimizes the window whether or
not anything is drawn there. A test (`window_control_labels_are_only_painted_while_hovering_the_bar`)
pins the invisibility, so this is deliberate design rather than an oversight.

In practice the risk is small — moving the pointer there sets `pointer_hover_pos` in the same
frame the click arrives, so the glyphs appear first. But combined with the previous finding (no
close confirmation), an affordance that is invisible by default and destructive when hit is worth
reconsidering. It also costs discoverability: a new window presents a bar with nothing in it.

**Impact:** Discoverability, and a small amount of risk stacked on top of the unconfirmed close.

**Fix:** Paint the controls at low opacity when not hovered rather than not at all, or keep the
`×` always visible and fade only minimize/maximize.

**Confidence:** Verified in code; unobserved.

### [Low] A whitespace-only output block offers copy buttons that do nothing

**Where:** `src/app/copy_blocks.rs:40-41`.

**Detail:**

```rust
let text = if block.kind == Kind::Input || releasing { Some(Blocks::text(&term, block)) } else { None };
if text.as_ref().is_some_and(|text| text.trim().is_empty()) { return None; }
```

For an `Output` block the text is only computed on the frame the button is released, so the
empty-text check does not run while merely hovering. A command whose output is whitespace (a
`printf '\n\n'`, a tool that emits only blank padding) therefore shows the hover highlight and
the copy button; on click, `copy_block_hover` returns `None`, `draw_copy_block` gets nothing, and
the button disappears without copying.

Genuinely empty output is already excluded upstream — `Blocks::at` cannot produce a block whose
`start.line > end.line` — so this is narrow.

**Impact:** A control that appears and then silently fails. Rare.

**Fix:** Compute the text for `Output` blocks on hover too (it is one `bounds_to_string` under a
lock that is already held), or skip the button when every row in the range is blank, which
`Blocks::blank` can already answer.

**Confidence:** Verified in code; unobserved.

## Worth checking in the next GUI pass

Not findings — questions the source raised that only a running window can answer.

- **The sigil completion menu's key claims.** `handle_sigil_key` takes Tab, Escape, Up and Down
  while the menu is on screen. The narrowness is well argued, but this is the layer with no tests
  (see 05) and the failure mode — "Up stopped recalling history" — is exactly the class the
  `release_chrome_focus` bug belonged to.
- **Typing sounds during modal chrome.** `app.rs:829` plays keystroke sounds while the settings
  window, palette or find bar is open. That is probably what you want, but it means a keystroke
  typed into a text field sounds identical to one going to the shell.
- **`@shortcut` + Enter opening the wrong shell** (01, Low) — visible immediately in a WSL or
  Git Bash pane.
- **The custom cursor.** `win/cursor.rs` answers `WM_SETCURSOR` from a subclass and
  `activate(false)` restores `IDC_ARROW` unconditionally rather than restoring what eframe wanted
  — so the pointer over a gutter, a resize edge or a settings widget should be checked to be the
  right shape after the terminal has had the pointer once.
